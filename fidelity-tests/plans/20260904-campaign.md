# Plan — a large round of error hunting for gdoc (draft, 2026-09-04)

Goal: find, minimise, classify and present the ways `gdoc` damages or fails to edit Google Docs,
across the whole space of documents people actually have, fast enough that dozens of agents can
run in parallel and a human can review the results in one sitting. Fixing comes later; this
plan ends with a library of confirmed, minimal, classified error cards and a list of what is
out of scope.

The pieces, each run by its own agents and connected only through files in the repo:

1. **Library** — one card per error, readable by a person in ten seconds.
2. **Hunt** — several ways of finding errors, ranked from cheapest to dearest.
3. **Reduce** — every find becomes a micro case (a seed, one command, a judge).
4. **Explore** — expand from confirmed cases into neighbours, chasing variety.
5. **Classify** — fixable in gdoc, fixable only with a different API call, or a limit of the
   platform; foreclose the last kind.
6. **Register** — limitations documented once, so hunting stops there and users are told.

Everything runs on the `micro` machinery already in `fidelity-tests/bin/gdt-micro`: a case is a
JSON file (seed built through the Docs API in about two seconds, one gdoc command, Target and
Allowed for the judge), and a run is one line of output plus before/after structure dumps.

## 1. Library — the visible interface

An **error card** has exactly four parts:

- a cropped screenshot of the relevant lines *before*, labelled "before";
- the same crop *after* the command, labelled "after";
- one plain sentence saying what was asked and what happened instead (the six sentences in
  the current showcase doc are the model: no jargon, one fact per clause);
- the command, gdoc's reply, and the case id in small print.

How the crops are made without a browser: micro documents contain nothing a PDF loses (no
comments, suggestions or chips), so `gdoc export --format pdf` on the seed doc and on the
edited doc, rendered with `pdftoppm` at 150 dpi, gives two images in a few seconds. The crop
is the vertical band containing the Target paragraph plus one line of context above and below,
located by matching the paragraph's text in the PDF's text layer (`pdftotext -bbox`). The two
crops are placed side by side with a thin frame and a caption. Cards for cases that need
comments or suggestions (developer-preview surface) fall back to the browser shooter we already
have; they are a minority and can be batched nightly.

Where the cards live:

- `fidelity-tests/micro/cards/<case>.png` and `<case>.md` (the sentence, the command, the
  reply, the class, the issue link), regenerated by `bin/gdt-card` from a case's latest result.
- A single **HTML gallery** (`micro/gallery.html`, generated by `bin/gdt-gallery`), built for
  fast review: cards in a grid, filters by class / command / construct / status, keyboard
  next/previous, a "mark reviewed / disagree" toggle that writes back to a local JSON so a
  review session leaves a trace. No Google Doc gallery; the tabbed showcase doc stays as the
  "look at the whole document" view and is regenerated from the same cases.
- `INDEX.md` gains a "micro" section: cases by class and status, with the last run's outcome.

Acceptance: a person who has never seen the suite opens the gallery and can say, for each card,
what went wrong, in under ten seconds, without reading the command.

## 2. Hunt — ways of finding errors, cheapest first

| # | Method | What it catches | Cost per case | Who runs it |
|---|---|---|---|---|
| H1 | **Command sweep**: for every gdoc write command and every seed construct in a grid, run the command on a minimal doc and judge with `gdt-diff` | everything that shows in the document structure: styles, paragraph properties, list membership, tables, footnotes, headers, named ranges | ~10 s, fully parallel, no browser | a script (`gdt micro`) driven by a generator |
| H2 | **Round-trip invariance**: `cat` → `write` (or `pull` → `push`) of an unchanged document must leave the structure unchanged; `edit` of X→Y then Y→X must return to the start | markdown fidelity, spacer paragraphs, list inheritance, anything lossy in export/import | ~15 s, parallel | a script (two commands per case, judge = before must equal after) |
| H3 | **Agent hunting on generated docs**: an agent with the CLI gets a small document seeded through the API from one or a few sentences and is told "make edits until something looks wrong; when it does, stop, write down what you did, then rebuild the smallest document that shows it and rerun" | choices only an agent makes (which command, which anchor), interactions between edits, wrong-but-plausible results, refusals | minutes; one throwaway doc per agent | many agents in parallel |
| H4 | **Metamorphic pairs**: the same edit on two documents that differ in one construct (bold run present or absent; inside a table or not) must produce the same text diff and no extra items | construct-specific damage, index arithmetic after emoji or chips | ~20 s, parallel | a script that derives pairs from a base seed |
| H5 | **Visual judge**: screenshots before/after read by a model | rendering only a reader sees: chip values, suggestion colours, pagination | minutes; needs a browser | the existing shooter + judge subagents, nightly |
| H6 | **Browser-built fixtures with agents**: the current fidelity suite | the agent-plus-CLI system on documents the API cannot build (comments, suggestions, chips, drawings) | hours per fixture | the existing skill, one fixture at a time |

Order of work: H1 and H2 first, because they are scripts and cover the most ground per hour;
H4 as the sweep grows; H3 continuously in the background; H5 and H6 only for classes the first
four cannot reach. Every method ends the same way: a case file in `micro/cases/` plus a result.

The five browser-built fixtures are not the base for this campaign. Their one remaining use is
as a quarry: each holds sentences and constructs that real documents have, and those are mined
into separate small seeds (one or a few sentences each) for H1–H4. Nothing new is run on the
fixtures themselves.

**Rate limits are the real budget.** Documents are free to create; what bounds the campaign is
the Docs and Drive API quota (per-minute, per-user and per-project). The runner therefore:
keeps one process-wide token bucket shared by all jobs, backs off on HTTP 429/403 with the
retry-after value, batches all seed requests of a case into as few `batchUpdate` calls as
possible (today: two or three per case), and records the calls-per-case count so the sweep size
can be planned from measured quota rather than guessed. A first task of the campaign is to
measure the effective limit with a throwaway burst and write it into `micro/README.md`.

**Reproducibility.** Drive documents are disposable (a nightly job trashes everything in the
`micro` folder older than a day), the repo is the record: every run stores the case file as it
was, the seed requests actually sent, the command, gdoc's version and output, and the before and
after structure dumps under `micro/results/<date>/<case>/`. Re-running a case file recreates the
document; a result directory alone is enough to regenerate its card without the document.

The H1 grid, first version. Rows are seed constructs; columns are commands.

- Constructs: bold / italic / strikethrough / underline / small caps / highlight / colour /
  font / size on part of a paragraph; link; sub/superscript; emoji and non-BMP text before the
  match; tab and NBSP inside; heading styles; alignment / spacing / indent; bullet, numbered,
  checklist (via preview API if possible) at levels 0–2; table cell (plain, merged, with a
  list); footnote; header and footer; named range and bookmark; second tab; horizontal rule;
  page break; inline image; same phrase twice in one paragraph; match at paragraph start / end /
  spanning a run boundary / spanning two paragraphs.
- Commands: `edit` (plain replacement, markdown replacement, `--all`, `--cell`, `--tab`,
  `--old-file/--new-file` multi-paragraph), `suggest`, `insert` (start/end), `write` (whole doc,
  `--tab`), `push`, `add-tab`, `comment --quote`, `reply`, `resolve`, `insert-image`,
  `replace-image`, `cells` (Sheets), `rename`, `mv`.
- That is roughly 35 × 20 = 700 cells, about two hours of wall clock at eight parallel jobs.
  Generated, not hand-written: `bin/gdt-micro-gen` turns a grid spec into case files.

## 3. Reduce — from a find to a micro case

Whatever the method, a find is only accepted into the library once it is a micro case that
reproduces on a fresh seed. The reducer is a separate agent (or the hunting agent's second
phase) with one job: given a description and a document id, produce the smallest seed
(fewest paragraphs, fewest styles) and the single command that reproduces the unexpected
items, and confirm by running `gdt micro` twice. It records provenance (which method, which
document, which agent transcript) in the case file. Reduction is also where duplicates are
caught: two cases with the same **signature** (see below) are the same error.

## 4. Explore — expanding from what we have

The space is large and the interesting errors cluster, so exploration should reward variety,
not depth. Three ideas from the literature map onto this setting directly:

- **Quality-diversity search (MAP-Elites)** — Mouret & Clune 2015, https://arxiv.org/abs/1504.04909.
  Keep an *archive* indexed by a small set of behaviour descriptors; keep the best example per
  cell; mutate elites to fill empty cells. Our descriptors: (command, construct near the match,
  where the match sits relative to the construct, what was damaged). A new case is worth
  keeping if it lands in an empty cell or beats the incumbent on minimality. This is the
  principle behind "foreclose the crowded regions": once a cell is filled, more cases in it add
  nothing.
- **Go-Explore** — Ecoffet et al. 2019, https://arxiv.org/abs/1901.10995. Return to promising
  states before exploring further. For us a "state" is a confirmed case; exploration from it
  means mutating one thing at a time (move the match one character, swap the construct, add a
  second paragraph, change the command flag) and keeping mutations that produce a *new*
  signature. Cases with many novel neighbours get explored more.
- **Metamorphic and differential testing** — Chen et al. 2018 survey,
  https://doi.org/10.1145/3143561; McKeeman's differential testing, 1998,
  https://www.cs.dartmouth.edu/~mckeeman/references/DifferentialTestingForSoftware.pdf. Relations
  we can assert without knowing the right answer: an edit that changes only text must change
  only text; the same edit applied to two documents differing in one construct must yield the
  same text change; cat→write on an unchanged document is the identity. Violations are finds
  without a human writing an Expected field.
- **LLM-driven diversity** — Rainbow Teaming (Samvelyan et al. 2024,
  https://arxiv.org/abs/2402.16822) is MAP-Elites with an LLM as the mutation operator and a
  judge for quality; Evol-Instruct (Xu et al. 2023, https://arxiv.org/abs/2304.12244) gives the
  mutation menu ("add a constraint", "deepen", "change the context"). For H3, the hunting
  agent's instructions are the mutation operator: hand it the archive's empty cells as a
  wish-list rather than a blank "find bugs".
- **Fuzzing with structure** — grammar-based/coverage-guided fuzzing (AFL; Zeller et al.,
  https://www.fuzzingbook.org/) is the ancestor of H1; our "coverage" is archive cells, since
  we cannot instrument Google Docs.

How it differs from those papers: we have no fitness other than "new signature, small seed",
the mutation operators are hand-listed and small, and the judge is the structural diff rather
than a model. That makes the loop cheap and deterministic; the LLM enters only in H3 and in
writing the card sentence.

The **signature** of a case: the set of `(property, position relative to match)` pairs among its
unexpected items, normalised — e.g. `{strikethrough:before-match, backgroundColor:inside-match}`
or `{alignment:paragraph}` or `{bullet:all-paragraphs}`. Two cases share an error if they share
a signature and a command. The archive is `micro/archive.json`: cell → best case, count of
cases seen, foreclosed flag.

## 5. Classify

Every archived case gets a class, decided by a separate classifier agent that reads the case,
gdoc's source for the command, and the Docs API reference (including the developer-preview
surface for comments and suggestions, which our account has):

- **CLI-fixable**: the API can do it precisely and gdoc chooses not to (rewriting a paragraph
  instead of the matched range; resetting paragraph style; not addressing footnote segments;
  markdown replacement inheriting the wrong list). Most of today's findings.
- **CLI-missing**: the API can do it and gdoc has no command (delete a table row, set nesting,
  set font size or highlight, accept or reject a suggestion if the preview surface allows it).
- **API-limit**: no API surface at all (tick a checklist box, edit a drawing, resize an image
  wrapped with text, anchor a comment through the public API). These go to the register.
- **Agent**: gdoc could; the agent chose badly. Feeds the skill and prompts, not the CLI.

The classifier writes `class`, `evidence` (API method or absence), and for CLI classes a
one-paragraph fix sketch into the case file. A human spot-checks a sample; disagreements go to
`CORRECTIONS.md` as today.

## 6. Register of limitations, and foreclosure

`fidelity-tests/LIMITATIONS.md`: one entry per API-limit class with the cases that prove it, the
API reference that shows the absence, and the user-facing sentence gdoc's README should carry.
Foreclosure rule: a hunting or exploring agent must check the archive and the register before
spending effort; cells marked foreclosed are skipped unless the agent can state, in one
sentence, what would be new about the case. The register is also the source for gdoc's
documented "cannot do" list.

## Agents and their boundaries

- **Sweeper** (script): generates and runs H1/H2/H4 cases; no judgement beyond `gdt-diff`.
- **Hunters** (agents, many in parallel): H3 on copies of fixtures or on generated messy
  docs; each ends by handing a description and a doc id to a reducer. Never read the archive's
  answers, only its empty cells.
- **Reducers** (agents): make micro cases; confirm twice; compute the signature; dedupe.
- **Explorer** (script plus a small agent): picks elites, applies mutations, runs the sweep on
  the results, updates the archive.
- **Classifier** (agent): assigns class and fix sketch; maintains the register.
- **Librarian** (script): cards, gallery, showcase, INDEX; runs after every batch.

No agent edits a fixture, a run copy or another agent's case file; each writes only under its
own id. Runs are recorded under `micro/results/<date>/`, so any card can be regenerated.

## Order of work and rough size

1. Cards and gallery from today's six cases (PDF-export crops). Half a day.
2. Grid generator and the first sweep of ~700 cells; archive with signatures. One day of
   building, two hours of running.
3. Round-trip and metamorphic scripts on the same seeds. Half a day.
4. Hunters: ten agents on copies of the five fixtures with the empty-cell wish-list; reducers
   behind them. One night.
5. Classifier over the archive; first `LIMITATIONS.md`. Half a day.
6. Explorer loop: three rounds of mutate-and-sweep. One day.
7. Report: what fraction of cells are filled, how many distinct signatures, the register, and
   the top ten CLI-fixable errors by breadth of cells they touch — that last list is the input to
   the fixing phase, where each case becomes a regression test that must go DONE.

## Decisions so far (2026-09-04)

1. Gallery: HTML only, optimised for one reviewer's speed.
2. Documents are unlimited; nightly cleanup of the `micro` Drive folder; the repo keeps every
   run reproducible (see Reproducibility above). Rate limits are the constraint to engineer for.
3. Hunters and sweeps work on API-generated documents seeded from one or a few sentences; the
   old fixtures are only mined for sentences and constructs.
4. Whether the preview API for comments and suggestions is callable directly with gdoc's
   credentials is being tested by a subagent; the result goes into `micro/README.md` and decides
   whether H1 gets comment and suggestion constructs.
