**Run a smaller campaign after validating the judge.** The micro approach is right; the proposed archive, census and agent organisation would currently scale misleading verdicts faster than useful discoveries. Recommendations below are ranked by impact.

1. **Make success an assertion, not the absence of collateral.** In [the runner](../bin/gdt-micro), `DONE` means some expected diff exists, not that the request succeeded; a nonzero command exit can still become `DONE`. An offline probe of [the judge](../bin/gdt-diff) classified `3 → 999` as expected for the case requesting `3 → 4`. Require exact replacement text/count, intended styles and preserved surroundings; separately record completion, collateral and command failure. Validate seed preconditions from the captured document. Failed captures, malformed JSON and judge failures must be `INVALID`, never clean; today's unchecked subprocesses and reused result directories can consume stale results. Calibrate with deliberately wrong text, missing styles, wrong-tab edits, anchor shrink and known-clean changes before generating more cases.

   Merely adding `commentAnchors` does **not** close the anchor blind spot: an offline probe confirmed that `normalise()` drops anchor `startIndex`/`endIndex`, making range-only changes equal. Compare anchor coverage against aligned text in an explicit suggestion view, preserving tab/segment identity. Audit passes as well as failures with an independent visual check; the [overnight report](../plans/20260902-overnight-report.md) already demonstrates why.

2. **Separate the search corpus from the evidence about everyday risk.** Diversity and relevance deserve separate reporting, but relevance should also allocate search effort. Start with a proposed 70% budget on observed workflows, 20% on constrained pairwise/boundary combinations and 10% on unrestricted exploration. Keep a fixed holdout of sampled workflows; adaptive discovery results cannot estimate a user failure rate. Report holdout completion and collateral separately from search yield and input coverage. “What was damaged” is an output descriptor: it cannot define the denominator for coverage that includes clean cases.

   `construct prevalence × intent frequency` assumes independence and measures the wrong exposure: a document containing a footnote says little about whether an edit touches it. README/help describe capabilities; test-agent transcripts reflect assigned adversarial tasks, not ordinary demand. Start with 30–50 recent genuine edit requests paired with their target context, deduplicated by workflow/document. Label selection bias and missing data; use coarse frequency bands, severity and detectability to rank fixes. Silent loss deserves priority even with weak frequency evidence. Retain a rare case if its consequence matters; the one-sentence rule is a presentation test, not a relevance test.

   A few hundred structural reads are cheap; representative sampling and useful skeleton extraction are the work. Pilot 30–50 documents, excluding test/generated copies and stratifying document type and recent use, before building `gdt-census`. Count edit-local contexts and co-occurrences, not just document-level presence. Neutral text must preserve UTF-16 lengths, punctuation, repeated matches and run boundaries; otherwise the skeleton removes the trigger. Structure also contains URLs, identities and object metadata: sanitize explicitly and retain employer-derived artifacts privately. Treat percentages as sample descriptions, not population weights.

3. **Budget actual requests; dozens of agents do not multiply throughput.** The final section's “six calls, one or two writes” does not describe today's harness. Its captures already use `--quiet`; it launches six capture subprocesses, plus move, command and judge—nine, not five. Offline seed inspection counted two seed writes for the style/bullet cases and three for the footnote case, before creation and the command. Tables currently write each populated cell separately.

   Use one dispatcher with per-account/project/API read/write budgets covering **subprocess traffic too**. A process-local bucket in each hunter is insufficient. Inspect configured quotas, then run a paced 20–30-case pilot recording endpoint counts, latency percentiles and throttles; do not begin with a saturation burst on the work account. Retry quota errors with bounded jittered backoff; distinguish permission errors and ambiguous write timeouts from safe retries.

   Concrete savings, beyond the plan's capture/judge changes:

   - Combine text insertion and subsequent styling in one seed `batchUpdate`; batch table fills in descending index order. Google explicitly permits ordered dependent subrequests and counts the batch as one request. Footnotes still need returned IDs. [Batch semantics](https://developers.google.com/workspace/docs/api/how-tos/batch).
   - Keep raw before/after `documents.get` results, including all tabs and explicit suggestion/comment views. Capture Drive comment/thread state only for relevant cases until parity with the preview response is verified. Keep one real CLI invocation; test `cat` separately rather than deriving its output and pretending it was exercised. Use `--quiet` for the bulk edit sweep, with a smaller default-mode/conflict cohort.
   - Deduplicate exact generated inputs offline; spend repeat runs and reduction only on novel failures. Render cards only for retained representatives. Use four workers initially, increasing toward eight only if measured latency leaves quota unused. Reserve budget for confirmation and other account activity; no personal-account spillover for employer-derived fixtures.

   Published Docs defaults are **60 writes and 300 reads/minute/user/project**, with project limits of 600/3,000; configured quotas can differ. [Quota reference](https://developers.google.com/workspace/docs/api/limits). Estimated budgets after the changes, assuming one command write:

   | Case | Docs writes | Docs reads | Other calls | Planning rate at 80% write budget |
   |---|---:|---:|---|---:|
   | Simple seed, Docs create | 3 | ≥3 | Drive move/state as used | 16/min |
   | Simple seed, Drive create-in-folder | 2 | ≥3 | Drive create + CLI state read | 24/min |
   | Footnote/table/suggestion or multi-command case | 3–5+ | ≥3 | Construct-dependent | 10–16/min or less |

   These are **estimates, not measured throughput**; the Drive-create path needs a pilot. Budget roughly 10–20 mixed executions/minute: 700 executions take 35–70 minutes; confirming every case twice would triple that. Reduction, previews, exports and human review are additional. Four seconds of isolated latency is not four seconds of sustainable quota cost. Track confirmed new fix families per hour as well as executions/minute.

4. **Deliver the fix list before building a search platform.** The overnight report attributes its collateral to paragraph rewriting; more font variants need not mean more fixes. First campaign: validate the six existing repros, run 60–100 applicable combinations around `edit`, `write`/`push`, `insert` and suggestion/comment anchors, then confirm and minimise one representative per suspected fix family. Keep a few longer operation sequences and UI-built examples; reducing everything to one command would discard state/history bugs, including already-flattened paragraphs masking subsequent damage.

   Defer MAP-Elites selection, ten hunters plus reducer/classifier agents, automatic skeleton generation, three explorer rounds and the interactive gallery. Use a JSONL ledger and Markdown fix table with request, minimal repro, evidence, suspected cause, severity and uncertainty. Render only the top representatives. Remove Sheets `cells` from the Docs grid; test rename/move with metadata expectations, and reject inapplicable combinations before spending calls. Stop after the planned coverage and one bounded expansion round; continue only when new fix families justify the cost. Do not stop a family after three duplicate neighbours: their enumeration order says nothing about its unexplored boundaries.

5. **Treat signatures as triage hints, not proof of duplicate bugs.** One paragraph rewrite can generate many property signatures; different causes can generate the same one. Group by suspected code path and preserve contrasting repros until a common fix is demonstrated. Keep both the minimal case and its original natural context; archive “best minimality” must not erase the evidence of relevance. For minimisation, preserve the *same failure predicate*, not merely any unexpected diff, and allow multi-command traces. Quarantine flaky cases rather than declaring them disproved.

   Replace definitive `API-limit` foreclosure with capability evidence dated by API surface, account/project and operation. Failure of one request does not prove impossibility. Separate inability to perform an operation from inability to preserve that construct during another edit. The plan's preview addendum already overturns earlier comments assumptions. Unknown classification remains unknown; it must not suppress hunting.

6. **Qualify the invariants and keep independent evidence.** `cat → write` is not automatically a structural identity: define the representable subset and separately report lost information outside it. `X → Y → X` requires unambiguous matches and checks after both steps; paired tests can agree while both are wrong. Compare against a small independent range-edit reference for supported operations. Keep semantic equivalence separate from raw JSON identity and test the normalization rules themselves.

   API seeds must be read back and checked against intended constructs, with a small UI-origin holdout for inheritance, lists, comments and suggestions. An API seed that never recreates a UI-produced terminal paragraph cannot establish safety there. Preserve PDFs/crops with the run: structure dumps alone cannot regenerate the promised visual cards after document cleanup. Crops must include the actual collateral, not just the target paragraph; invisible anchor changes need explicit evidence. Give every run a unique directory and temporary files: the current write case shares `/tmp/gdt-micro-write.md`. The showcase re-executes commands, so it is another run, not evidence of the original verdict.

7. **Keep the testing literature; demote the exploration analogies.**

   - [Metamorphic testing](https://nottingham-repository.worktribe.com/output/925152/metamorphic-testing-a-review-of-challenges-and-opportunities) is directly relevant, provided relations have preconditions. Differential testing needs an independent implementation, not merely a before/after diff. Add [Csmith](https://users.cs.utah.edu/~regehr/papers/pldi11-preprint.pdf) for valid generators and differential oracles.
   - The biggest omissions are [delta debugging](https://www.st.cs.uni-saarland.de/papers/tse2002/) for automated reduction and [constrained combinatorial testing](https://csrc.nist.gov/projects/automated-combinatorial-testing-for-software) for replacing an indiscriminate Cartesian grid. Minimise locally where possible, then confirm live. Google is opaque, but gdoc's parser/request-building code can still be instrumented locally.
   - [MAP-Elites](https://arxiv.org/abs/1504.04909) and [Rainbow Teaming](https://arxiv.org/abs/2402.16822) justify diverse archives, not the proposed duplicate or stopping rules. [Go-Explore](https://arxiv.org/abs/1901.10995) adds little until long stateful traces matter; [Evol-Instruct](https://arxiv.org/abs/2304.12244) supplies mutation inspiration, not evidence of bug-finding efficiency. A seeded mutation queue is enough initially.
